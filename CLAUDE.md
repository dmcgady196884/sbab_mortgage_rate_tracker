# Project Instructions

## Workflow
- ALWAYS discuss your plan before writing/editing code
- Do NOT run workflows or trigger GitHub Actions without explicit approval
- When fixing bugs, explain the root cause first, then propose the fix
- Ask clarifying questions rather than making assumptions
- Narrate what you're doing - don't run tools silently in rapid succession

## Multi-Session Work
- For multi-step refactoring or complex tasks spanning sessions, create a context checkpoint file (e.g., `REFACTORING_PLAN_DELETE_WHEN_DONE.md`)
- Include: strategic plan, current status, what's done, what's remaining, key design decisions
- Commit to git so it survives session death
- Delete the file (and commit that deletion) after merging - git history is sufficient for archaeology

## Test Fixtures
- Test fixtures must use EXACT same logic as production code
- Never simplify or change algorithms "for testing" - that's not a test
- Check expected data formats by reading the code that consumes them, not inventing formats
- When a workflow step has `continue-on-error: true`, failures are silent - investigate before assuming success

## This Project
- PRs are created when SBAB changes pricing logic (discount surfaces, boundaries, etc.) - not every run
- If a test fixture simulates a pricing change and no PR is created, something is broken
- Prominent boundaries (`PROMINENT_LTV_BREAKS` / `PROMINENT_VOL_BREAKS` in `io_contracts.py`; empty by default) are always added to the break lines when set
- The grid deep scraper uses a specific probe grid (±offsets around key points) - fixtures must match exactly 

## Hardcoded values and assumptions
- All hardcoded constants (sentinels, thresholds, prominent boundaries, valid maturities, etc.) belong in `io_contracts.py` — the central assumption registry
- If a constant is deliberately placed elsewhere, document why in a comment, and note the exception in both `CLAUDE.md` and `README.md`
- API JSON structure is validated by `assert_api_response()` in `io_contracts.py`, called immediately after `json.load()` in the scraper
- **Exception:** `_DATA_FILES`, `_DISCOUNT_SURFACE_GLOB`, `_CHANGE_DESCRIPTIONS` in `src/7_open_PR_with_updates_to_main.py` stay local to that file. Unlike the registry's sentinels/thresholds/prominent boundaries, these aren't assumptions about SBAB's pricing data — they're PR-formatting details (which filenames this one step stages, and how it describes them in the commit message/PR body) with exactly one reader. The bin-membership convention (`LTV_BIN_RIGHT_CLOSED`/`VOL_BIN_RIGHT_CLOSED`), by contrast, *is* a real pricing assumption shared by multiple call sites, so it lives in `io_contracts.py`.

## Modus operandi
- Indentation: match the existing file's style (most files use 4-space; `io_contracts.py` uses tabs). Never mix within a file.
- Make this as lightweight as possible
- Only version-control small files
- Keep this codebase as minimalistic and human-readable as possible. When making new code, consult with the structure of the older code before formulating a development plan.

## Overall goal of this project:
- Regularly extract SBAB's prices for mortgages, via a public (but not very publicized) API
- Run daily github actions to monitor prices, light run (~800 API calls)
- If price change, action creates feature-branch, triggers deep-scraper, then consistency check (same shallow search as in the no-change result, in item above)
- If prices updated, new rows appended to minimalistic .csv-files which are sufficient to reconstruct full pricing behavior, and .png-files visualizing the pricing are also to be updated (newly deprecated rows/images are "closed" with injecting non-null valid_to dates, and new rows/images are created with "valid_from"-dates equal to the date of the daily-run discovering the change, and "valid_to"="current" xor null, where appropriate)
- If updated, then whichever run that finds them includes these minimal files in the PR generated by daily run
- After analysis finishes, email is sent out to registered email addresses; if prices change, PR must be linked
- Committed files are meant to be lightweight (do not commit big changes)
- Code is meant to be simple and readable — no clever abstractions
